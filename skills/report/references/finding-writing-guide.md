## Finding Structure

Each detailed finding MUST include all of the following fields:

### Reference ID

Unique identifier following the format:
- **Web2:** `WSTG-v42-<CATEGORY>-<NN>` (e.g., `WSTG-v42-INPV-01`)
- **Web3:** `SWC-<NNN>` (e.g., `SWC-107`)

### Title

Concise vulnerability name. Should be specific and descriptive.

**Good:** "SQL Injection in Login Form"
**Bad:** "Vulnerability in Authentication"

### Affected Asset

Host, URL, port, contract, or component affected by the vulnerability.

**Examples:**
- `https://example.com/login`
- `api.example.com:443`
- `Vault.sol — withdraw() function`
- `0x1234...abcd — transfer() function`

### Severity

Calculated using the appropriate scale:
- **Web2:** CVSS v3.1 (Critical / High / Medium / Low / Informational)
- **Web3:** Immunefi (Critical / High / Medium / Low / Informational)

### CVSS/Impact

Calculated score with vector string:
- **Web2:** `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` — Score: 9.8
- **Web3:** Impact description (e.g., "Direct theft of user funds")

### CVE/CWE/SWC

Classification identifier if applicable:
- **CVE:** `CVE-2024-1234` (if assigned)
- **CWE:** `CWE-89` (SQL Injection)
- **SWC:** `SWC-107` (Reentrancy)

### Description

What the vulnerability is, how it can be exploited, and potential damage. Should be:
- Clear and concise
- Technical but accessible
- Specific to the finding
- Free of unnecessary jargon

### Evidence

Tool output, screenshots, or PoC — with provenance label. Must be:
- Reproducible
- Verifiable
- Clearly labeled with source

### Business Impact

What this means for the organization in business terms. Should connect the technical finding to business risk.

### Remediation

Specific, actionable steps to fix the issue. Must be:
- Specific enough for an engineer to act on
- Prioritized by effort and impact
- Realistic and achievable

### Provenance

- `tool-proven` — Backed by captured tool output
- `model-asserted` — Hypothesis based on observed behavior, not directly captured

## Writing Style

### DO:
- Use clear, concise language
- Be specific and factual
- Use active voice
- Write for a technical audience (developers, security engineers)
- Include code snippets where relevant
- Reference specific functions, lines, or components
- Use consistent terminology (define in methodology)

### DON'T:
- Use vague language ("might," "could possibly," "it seems")
- Include unnecessary technical jargon
- Write in passive voice
- Make assumptions without evidence
- Include unrelated information
- Use inflammatory language

### Language Guidelines

| Instead of... | Use... |
|---------------|--------|
| "The application might be vulnerable" | "The application is vulnerable" |
| "It seems like there could be an issue" | "The following issue was identified" |
| "This is a critical vulnerability" | "This vulnerability has a CVSS score of 9.8" |
| "The developers should fix this" | "Apply parameterized queries to prevent SQL injection" |

## Evidence Requirements

### Reproducible

Evidence must be reproducible. Include:
- Exact commands used
- Tool names and versions
- Timestamps
- Environment details

### Verifiable

Evidence must be verifiable. Include:
- Screenshots with timestamps
- HTTP request/response pairs
- Tool output with clear labels
- Transaction hashes (for web3)
- Log entries with timestamps

### Provenance Labels

Every piece of evidence must have a provenance label:

- **`tool-proven`** — Backed by captured tool output (screenshot, scan result, HTTP request/response, log entry, transaction hash). The evidence is reproducible.
- **`model-asserted`** — Hypothesis generated by the tester based on observed behavior but not directly captured in tool output. Must be clearly labeled as unverified.

### Evidence Format

```markdown
#### Evidence

**Source:** [Tool name], [Version]
**Timestamp:** [ISO 8601 timestamp]
**Provenance:** tool-proven

[Tool output, screenshot description, HTTP request/response, etc.]
```

## Remediation

### Specific

Remediation must be specific enough for an engineer to act on:

**Bad:** "Fix the SQL injection vulnerability."
**Good:** "Replace the dynamic SQL query with a parameterized query using prepared statements. For example, change `SELECT * FROM users WHERE id = " + userId` to `SELECT * FROM users WHERE id = ?` with the userId passed as a parameter."

### Actionable

Remediation must be actionable:

**Bad:** "Improve input validation."
**Good:** "Implement allowlist validation on the username field. Accept only alphanumeric characters and underscores, with a length between 3 and 32 characters. Reject all other input with a 400 Bad Request response."

### Prioritized

Remediation should be prioritized by effort and impact:

| Priority | Effort | Impact | Example |
|----------|--------|--------|---------|
| P0 | S | Critical | Block active attack paths |
| P1 | M | High | Fix high-severity findings |
| P2 | L | Medium | Configuration changes |
| P3 | L | Low | Best practice improvements |

### Code Examples

Include code examples for remediation where applicable:

```solidity
// BAD: Vulnerable to reentrancy
function withdraw() external {
    uint256 balance = balances[msg.sender];
    require(balance > 0, "No balance");
    (bool success, ) = msg.sender.call{value: balance}("");
    require(success, "Transfer failed");
    balances[msg.sender] = 0;
}

// GOOD: Checks-Effects-Interactions pattern
function withdraw() external {
    uint256 balance = balances[msg.sender];
    require(balance > 0, "No balance");
    balances[msg.sender] = 0;  // Effects first
    (bool success, ) = msg.sender.call{value: balance}("");  // Interactions last
    require(success, "Transfer failed");
}
```

## Common Mistakes

### 1. Vague Descriptions

**Bad:** "The application has a security issue that could allow an attacker to access sensitive data."
**Good:** "The login form at https://example.com/login is vulnerable to SQL injection, allowing an attacker to bypass authentication and extract the entire user database."

### 2. Missing Evidence

**Bad:** "A vulnerability was found in the authentication system."
**Good:** "A vulnerability was found in the authentication system. Evidence: [tool output showing the vulnerability]."

### 3. Generic Remediation

**Bad:** "Fix the vulnerability."
**Good:** "Implement parameterized queries to prevent SQL injection. Use prepared statements with bound parameters instead of string concatenation."

### 4. Inconsistent Severity

**Bad:** Assigning severity by intuition without calculation.
**Good:** "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H — Score: 9.8 (Critical)"

### 5. Missing Provenance

**Bad:** Presenting a model-asserted finding as tool-proven.
**Good:** "Provenance: model-asserted. This finding is based on observed behavior but has not been confirmed with captured tool output. To confirm, run [specific test]."

### 6. Duplicate Findings

**Bad:** Presenting the same vulnerability found by multiple tools as separate findings.
**Good:** Merge into a single finding with multiple evidence sources, noting "Also detected by [other tools]."

### 7. Incomplete Fields

**Bad:** Missing one or more required fields (description, evidence, impact, remediation, provenance).
**Good:** All required fields present and complete.

## Examples

### Good Finding

```markdown
### WSTG-v42-INPV-01: SQL Injection in Login Form

| Field | Value |
|-------|-------|
| **Reference ID** | WSTG-v42-INPV-01 |
| **Severity** | Critical |
| **CVSS v3.1** | 9.8 — CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H |
| **CWE** | CWE-89 |
| **WSTG** | WSTG-INPV-05 |
| **Affected Asset** | https://example.com/login |
| **Provenance** | tool-proven |
| **Status** | Open |

#### Description

The login form at https://example.com/login is vulnerable to SQL injection. The username parameter is directly concatenated into the SQL query without sanitization or parameterization, allowing an attacker to inject arbitrary SQL code. This can be exploited to bypass authentication, extract sensitive data from the database, or modify database contents.

#### Evidence

**Source:** sqlmap 1.7.2
**Timestamp:** 2024-01-20T14:32:00Z
**Provenance:** tool-proven

```
$ sqlmap -u "https://example.com/login" --data="username=admin&password=test" --batch
...
Parameter: username (POST)
    Type: boolean-based blind
    Title: AND boolean-based blind - WHERE or HAVING clause
    Payload: username=admin' AND 1234=1234--&password=test
...
back-end DBMS: MySQL >= 5.0
available databases [3]:
[*] information_schema
[*] mysql
[*] webapp_db
```

#### Business Impact

An attacker could exploit this vulnerability to gain unauthorized access to the application, extract sensitive customer data (including personally identifiable information), modify or delete database contents, and potentially use the database server as a pivot point to attack other systems on the network. This could result in regulatory fines, reputational damage, and loss of customer trust.

#### Remediation

Replace the dynamic SQL query with a parameterized query using prepared statements:

```python
# BAD: Vulnerable to SQL injection
query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
cursor.execute(query)

# GOOD: Parameterized query
query = "SELECT * FROM users WHERE username = %s AND password = %s"
cursor.execute(query, (username, password))
```

Additionally, implement input validation to reject suspicious input and apply the principle of least privilege to the database account used by the application.

#### Also Detected By

- Nessus (Plugin ID: 10719)
- Burp Suite Professional (Active Scan)
```

### Bad Finding

```markdown
### Finding 1: SQL Injection

The application has a SQL injection vulnerability. This is a critical issue that needs to be fixed immediately.

#### Description

There is a SQL injection in the login form. An attacker could use this to access the database.

#### Evidence

We tested the login form and found that it is vulnerable.

#### Impact

This could allow an attacker to access sensitive data.

#### Remediation

Fix the SQL injection by using proper input validation.
```

**Why this is bad:**
- Vague title ("SQL Injection" — where?)
- No reference ID
- No CVSS score or vector
- No CWE/WSTG reference
- Vague description
- No specific evidence (no tool output, no timestamp)
- No provenance label
- Generic remediation
- No business impact details

## Checklist

Before finalizing a finding, verify:

- [ ] All required fields present (Reference ID, Title, Affected Asset, Severity, CVSS/Impact, CVE/CWE/SWC, Description, Evidence, Business Impact, Remediation, Provenance)
- [ ] Reference ID follows correct format
- [ ] Severity calculated using appropriate scale
- [ ] CVSS vector string included (web2)
- [ ] Description is clear, concise, and specific
- [ ] Evidence is reproducible and verifiable
- [ ] Evidence has provenance label
- [ ] Business impact connects to organizational risk
- [ ] Remediation is specific and actionable
- [ ] Remediation includes code examples where applicable
- [ ] No vague language
- [ ] No missing fields
- [ ] Consistent with methodology terminology
